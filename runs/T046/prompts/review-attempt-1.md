# ROLE

# Role — Reviewer

## Mission

Vérifier qu’une implémentation respecte :
- le ticket
- le plan
- les conventions
- l’architecture
- les contraintes sécurité/qualité

## Tu dois

- détecter les dérives de scope
- détecter les violations architecture
- vérifier les impacts potentiels
- vérifier la cohérence mémoire/documentation
- proposer des corrections concrètes

- réécrire complètement le code
- introduire un nouveau scope
- accepter des comportements implicites dangereux

# SKILL: code-quality

# Skill — Code Quality

## Objectif

Produire des changements simples, lisibles, robustes et faciles à reviewer.

## Règles

- privilégier le code simple avant le code sophistiqué
- utiliser des noms explicites
- garder des fonctions courtes et lisibles
- éviter la magie cachée
- gérer les erreurs explicitement
- ajouter des logs utiles sans bruit excessif
- éviter les dépendances inutiles
- conserver un changement borné au ticket

## Refuser si

- le code devient inutilement complexe
- le ticket introduit une dépendance non justifiée
- les erreurs sont masquées
- les changements dépassent le scope demandé

# SKILL: refactor-safety

# Skill — Refactor Safety

## Objectif

Limiter les régressions et les dérives de scope lors des modifications.

## Règles

- modifier uniquement le périmètre demandé
- éviter les refactors transversaux implicites
- préserver les comportements existants
- maintenir la compatibilité sauf demande explicite
- privilégier des changements incrémentaux

## Refuser si

- le ticket dérive vers une réécriture globale
- plusieurs couches sont modifiées sans justification
- le comportement change silencieusement

---

# SKILL: security

# Skill — Security

## Objectif

Réduire les risques de sécurité et éviter les comportements dangereux.

## Règles

- ne pas exposer de secrets dans logs ou documentation
- limiter les permissions au strict nécessaire
- éviter les exécutions implicites dangereuses
- valider les entrées externes
- documenter les impacts sécurité importants
- éviter les comportements destructifs implicites

## Refuser si

- des secrets sont hardcodés
- des données sensibles sont logguées
- une opération destructive n’est pas explicitement contrôlée

# T046 — Replace the dark interface with a modern light visual theme

**Source**: GitHub Issue #91

## Description

## Context
The current Timizer-like interface uses a predominantly black background that feels too dark and visually heavy. The application should look like a modern professional SaaS product rather than a developer-oriented dark dashboard.

## Goal
Introduce a bright, modern, business-oriented visual theme across the whole application.

## Description
Replace the current dark global background with a light neutral page background, white or lightly tinted content surfaces, subtle borders, restrained shadows, and a professional accent colour. Review all text, cards, controls, dialogs, navigation elements, tables, and calendar states so they remain readable and visually coherent.

The result should feel contemporary, calm, spacious, and suitable for producing and signing monthly CRA documents. Avoid excessive gradients, neon colours, pure black surfaces, and overly decorative effects.

## Out of Scope
- Changing CRA business rules.
- Rebuilding backend APIs.
- Adding a user-selectable dark mode.

## Acceptance Criteria
- [ ] The default application background is light rather than black.
- [ ] Main content surfaces use a coherent hierarchy of light backgrounds.
- [ ] Text contrast remains accessible.
- [ ] Borders and shadows are subtle and consistent.
- [ ] Buttons, inputs, dialogs, cards, tables, and calendar states follow the new theme.
- [ ] No component retains an accidental dark-theme style.
- [ ] Desktop and mobile screenshots demonstrate a coherent professional visual identity.
